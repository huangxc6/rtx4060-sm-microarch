# Round 12：L1I / L0I（指令缓存）

数据来源：`results/20261115-230119/`（Round 12 单轮）。

**这一轮用的是外部测试程序**：`third_party/icache_b300_pkg/`（面向 B300/sm_103 的
指令缓存微基准）。它原样跑不了（需要 nvcc + Linux + 独占 sm_90+），
但内核是纯 device 代码，所以用本工程的 nvrtc 链路重新驱动——内核生成器照用，
host 编排换成 Python。移植细节见 §4。

---

## 0. 结论

| 项 | 实测 | 置信度 |
|---|---|---|
| **L1I 容量** | **64–80 KiB**（拐点在 64 KiB 与 80 KiB 之间） | 高 |
| 容量内的每指令周期 | **1.01–1.13 cycles**（单 warp，理论下限 1.00） | 高 |
| 容量外（80–128 KiB） | 2.43–2.52 cycles/指令（≈2.2×） | 高 |
| 192 KiB 以上 | 3.1–3.9 cycles/指令 | 高 |
| 跨调度器分区（warp0 + warp1） | **互不干扰**（cpi 完全不变） | 高 |
| 同分区两份代码（2 × 4/8/16 KiB） | **没有额外代价**（只是 2 warp 抢发射槽的 2×） | 中 |

## 1. L1I 容量：64–80 KiB

方法：`fp` 家族的每个内核是一段**完全展开、无分支**的 FMA 指令流，代码足迹可控。
单 warp 跑 `iters` 遍，取 `clock64` 差值，除以执行的指令数。

| 名义足迹 | SASS 实测代码量 | 周期/指令 |
|---:|---:|---:|
| 4 KiB | 5.1 KiB（328 条） | 1.128 |
| 16 KiB | 17.1 KiB（1096 条） | 1.041 |
| 32 KiB | 33.1 KiB（2120 条） | 1.022 |
| 48 KiB | 49.1 KiB（3144 条） | 1.014 |
| 56 KiB | 57.1 KiB（3656 条） | **1.012** |
| 64 KiB | 65.1 KiB（4168 条） | 1.086 |
| **80 KiB** | **81.1 KiB（5192 条）** | **2.431** ← 台阶 |
| 96 KiB | 97.1 KiB（6216 条） | 2.431 |
| 128 KiB | 129.1 KiB（8264 条） | 2.522 |
| 144 KiB | 145.1 KiB（9288 条） | 3.095 |
| 192 KiB | 193.1 KiB（12360 条） | 3.251 |
| 512 KiB | 513.1 KiB（32840 条） | 3.924 |

三条读法：

1. **64 KiB 以内是 1.01–1.13 cycles/指令**。理论下限是 1.00（单 warp 每周期 1 条），
  所以 56 KiB 时的 1.012 说明指令供给几乎没有开销。
2. **64 → 80 KiB 之间出现 2.2× 的台阶**（1.086 → 2.431）。这就是 L1I 装不下的分界。
   考虑到 SASS 实测的代码量在 65.1 → 81.1 KiB 之间跨越，**L1I 容量约 64–80 KiB**。
3. **过了拐点不是干脆掉到 DRAM 级别**：80–128 KiB 稳定在 2.43–2.52（约 2.2×），
   到 144 KiB 才到 3.1，512 KiB 到 3.9。这符合"每行只取一次、命中率随足迹渐变"的预期：
   代码是按顺序流式执行的，L1I 用类似 FIFO/流式的替换，命中率随足迹平滑下降。

顺带一个交叉验证：`fp_0004k` 每个迭代 4 KiB 名义代码、SASS 328 条指令，
每指令 16 B ⟹ 5.1 KiB 实际代码；乘以迭代数 1048 得到的执行指令数（262,000）
与 `TARGET_INSTR = 2^18` 的设计值吻合 ✓——说明这套归一没有跑偏。

## 2. L0I：同一分区上的两份代码没有额外代价

`dual` 家族每个内核算两份代码（body A、body B），按 `roles` 的 4 bit/warp 指定每个 warp
跑哪一份。Round 4/6 已确认 **warp 0 与 warp 4 落在同一个调度器**，warp 0 与 warp 1 不同。

| 配置 | 4 KiB/份 | 8 KiB/份 | 16 KiB/份 |
|---|---|---|---|
| warp0 单独跑 A | 1.128 | 1.089 | 1.044 |
| warp0+warp1 同代码（不同分区） | 1.128 / 1.128 | 1.089 / 1.089 | 1.044 / 1.044 |
| warp0+warp1 不同代码（不同分区） | 1.128 / 1.128 | 1.091 / 1.091 | 1.045 / 1.045 |
| **warp0+warp4 同代码（同分区）** | 2.131 / 2.131 | 2.073 / 2.075 | 2.034 / 2.038 |
| **warp0+warp4 不同代码（同分区）** | 2.156 / 2.155 | 1.560 / 2.104 | 2.040 / 2.040 |

两条结论：

1. **跨分区完全互不干扰**：warp0 与 warp1（不同调度器）无论跑同代码还是不同代码，
   每指令周期都和不加第二个 warp 时**一模一样**。说明每个分区有自己的指令路径，
   或者共享的 L1I 容量远大于两份小代码。
2. **同分区变成 2.0–2.16 cycles/指令**，但这是**发射争用**的必然结果
   （两个 warp 抢一个调度器的 1 条/周期 ⟹ 每个 warp 0.5 IPC ⟹ 2 cycles/指令），
   而不是 i-cache 失效。
   证据：**"同代码"和"不同代码"在同一尺寸下几乎没差别**
   （4 KiB：2.131 vs 2.156；16 KiB：2.034 vs 2.040）。
   若 L0I 容量不够，两份不同代码会互相驱逐、明显更慢——实测没有。
   ⟹ **在 2 × 16 KiB 的规模上，没有观测到 L0I 容量限制**（L0I ≥ 32 KiB，或不存在独立的 L0I）。

（8 KiB 那行的 `w0=1.560` 是个反常值，只有一次出现的孤立点，未复现，不作为结论。）

## 3. 这三条数据有什么用

1. **解释了本工程其它测量为什么"干净"**：Round 1/2 的所有延迟与吞吐内核都是
   几百到一千条指令的直线代码（≤16 KiB），**完整装在 L1I 里**。
   所以那些数字不含取指开销，`1.012 cycles/指令` 这个余量就是全部开销。
2. **给出小内核的适用边界**：一个 SM 上的直线代码一旦超过约 64 KiB，
   执行效率会掉到 44%（2.43 cycles/指令）。这对"把循环完全展开"的优化手段是个硬约束
   ——展开到 80 KiB 就开始赔本了。
3. **跨分区不共享指令**：两个 warp 放不同分区不会因为代码不同而互相拖累，
   所以"把不同 kernel 放不同 SM"不会带来指令侧的额外成本。

## 4. 移植记录（怎么把它跑在 sm_89 上）

原包的 `tools/standalone.sh` 需要 Linux + nvcc + `make` + 独占 sm_90+ 卡，本机全不具备。
可移植的部分是它**生成出来的内核**：

1. `python gen_kernels.py --out-dir build --families fp,dual` 生成 43 个内核
   （纯标准库，本机可直接跑）。
2. 生成的头文件末尾带一张 **host 侧名册** `static const KernelInfo kKernels[]`，
   引用了 `KernelInfo`/`KIND_*` 等只在 host 侧定义的东西。nvrtc 只编 device 代码，
   所以从那里**截断**再编译。
3. 内核签名是 `__global__ void name(BenchArgs args)`——**结构体按值传**。
   `cuLaunchKernel` 的 `kernelParams` 本来就是 `void**`，每个元素指向"参数值"，
   所以只要用 ctypes 镜像出同样的 168 字节布局，把指向它的指针塞进数组即可。
4. `record()`、`c_array`、`kBlockThreads` 这些在 `icache_bench.cu` 里定义、被内核引用，
   用一个小 shim 补上。

没搬的部分：`cf`（行大小/组相联）、`qd`（分区带宽）、`vis`（跨分区可见性）、
`seq`（替换策略）、`bw`（取指带宽矩阵）、`gpcmap`（需要 sm_90 的 thread block cluster）。
其中 `cf`/`qd` 的内核是几万行的内联汇编冲突链，语义依赖完整 host 编排才能解读，
留给以后。

## 5. 没做到的

1. **L1I 容量只能夹在 64–80 KiB 之间**（生成器的尺寸网格就是 64/80）。
2. **L1I 的延迟**没测（只测了吞吐/命中率）。
3. **取指带宽**（每周期多少字节）没测——需要 `bw` 家族。
4. **行大小与组相联**没测（`cf` 家族没搬）。
5. **替换策略**没测（`seq` 家族没搬）。
6. **L0I 是否存在**仍未确定：只能说"2 × 16 KiB 规模上没有观测到容量限制"。
