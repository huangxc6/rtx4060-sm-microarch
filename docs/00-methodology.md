# 测量方法论

本工程的目标是**用微基准反推** NVIDIA GeForce RTX 4060（AD107，sm_89）的 SM 微架构，
而不是抄规格书。因此所有结论必须满足：**可复现的测量 → 可证伪的推论 → 交叉验证**。

## 0. 环境约束（决定了方法论）

| 约束 | 实情 | 对方法的影响 |
|---|---|---|
| 权限 | 非管理员 | `nvidia-smi -lgc` 无法锁频；GPU 频率随负载/温度漂移 |
| 驱动 | 610.88, WDDM | 无独占模式；桌面合成会抢占 SM 与内存带宽 |
| 工具链 | 无 CUDA Toolkit | 用 pip 的 `nvrtc` + `cuda-python`(driver API) 做 JIT |
| 现状 | P3 空闲态 285 MHz | 任何"纳秒"级结论都不可靠，**必须用周期数** |

## 1. 核心原则：只信周期，不信纳秒

因为无法锁频，绝对时间不可复现。所有测量都以 **SM 时钟周期（cycle）** 为单位：

- 内核内用 `%clock64` 读取 SM 周期计数器，在测量区间前后各取一次，差值即周期数。
- `%clock64` 是每 SM 独立的 64 位周期计数器，不受频率缩放影响，是本工程的主时钟。
- 需要换算成频率时，用 `%globaltimer`（纳秒）与 `%clock64` 同步采样：
  `f_SM = Δclock64 / Δglobaltimer`。这比 `nvidia-smi` 的采样值精确得多，且可在内核执行中瞬时测得。

**由此得到的指标天然是"每周期"量（ops/cycle、cycles/op），这是微架构的固有属性，与频率无关。**

## 2. 消除时钟漂移与噪声

1. **预热（boost priming）**：每次测量前连续跑 ~200 ms 的满载内核，把 GPU 从 P3 拉到 boost 态，
   并在正式测量期间保持高负载，避免掉回低频。
2. **区间内取周期**：每次测量重复 R 次，取**最小值**（min 对"最干净的一次执行"最敏感，
   噪声只会让周期变多，不会变少）。median 作为稳健性对照。
3. **差值法消固定开销**：对同一内核取两个不同迭代数 `N1 < N2`，
   `per_op_cycles = (C(N2) - C(N1)) / (N2 - N1)`。这消掉了内核启动、`clock64` 读取、
   参数设置等全部固定开销。本工程默认用此法（`bench.delta()`）。
4. **桌面干扰**：用 1 个 CTA 占 1 个 SM 做单 SM 测量时，其余 SM 空闲，
   桌面合成进程可能落在同一个 SM 上。用足量 CTA（占满所有 SM 且每 SM 多 CTA）可以靠
   "平均掉"干扰，但单 SM 精确测量必须多轮取 min。记录 `nvidia-smi` 的 util 作为环境注脚。

## 3. 每类量的测量模板

### 3.1 指令延迟（latency）
- 构造**完全串行的依赖链**：第 i 条指令的操作数是第 i-1 条的结果。
- 用 `asm volatile` 写指令，阻止编译器重排/合并/消除。
- 每条指令前不得有其它指令插入（用完全展开的 `#pragma unroll` 常数循环）。
- `latency = Δcycles / ΔN`。
- 陷阱：编译器可能把 `add` 优化成别的、或用 `IADD3` 三操作数形式；必须用 SASS 反汇编核对
  （`harness/sass.py`），本工程每条延迟数据都附 SASS 证据。

### 3.2 吞吐（throughput）
- 构造**完全独立**的指令流（`N` 条互不依赖），并让 warp 数足够填满流水线。
- `throughput = 总操作数 / Δcycles`，单位 ops/cycle/SM。
- 关键：单 warp 通常无法打到峰值（发射受限），必须做 **warp 数扫描** 找到饱和点，
  饱和点本身就是"每 SM 最大并发 warp / 发射宽度"的证据。
- 结果应接近 2 的幂（32/64/128/256），否则说明存在额外瓶颈（寄存器 bank、发射端口）。
- **归一必须精确到指令类别**，不能只数"SASS 总条数"：
  * `add.u32` 会被 ptxas 两两融合进一条 `IADD3`（一条顶两次加）；
  * `mma.sync` 会被插入 `MOV`/`LDG` 之类的搬运指令，且**条数随迭代数增长**。
  两种情形下按总条数归一都会系统性地算错（实测分别高估 2× 和 1.5×）。

### 3.3 存储层次（latency + capacity）
- **指针追逐（pointer chasing）**：数组内容为随机环状指针链，每个节点依赖上一个节点地址，
  天然串行，无法被预取或并发掩盖。
- 扫描工作集大小 `S`，看 `latency(S)` 的台阶 → 每一级缓存的**容量**与**延迟**。
- 步长（stride）扫描 → 缓存行大小 / sector 大小 / TLB 页大小。
  台阶出现在 `stride = 32B`（sector）与 `128B`（line）处。
- 用 `__ldg` / `ld.global.nc` / `ld.global.cg` / `.cv` 等 PTX cache operator 分别测，
  区分 L1 命中与"绕过 L1"。

### 3.4 结构参数（SM 数、warp 数、bank 数）
- **SM 计数**：固定每 CTA 工作量 `t`，扫 CTA 数 `G`，
  `cycles(G) ≈ ceil(G / SM_count) × t` 呈阶梯 → 台阶宽度即 SM 数。
- **warp 调度器数**：扫每 SM 的 warp 数，`throughput` 阶梯上升，台阶数 = scheduler 数。
  同时用"每 warp 独立计数器"看不同 warp 的 issue 分布。
- **共享内存 bank**：固定 warp 内 32 线程的访问地址模式（stride 0/1/2/.../32），
  冲突导致的周期数台阶 → bank 数、bank 宽度、是否支持广播/多播。
- **寄存器文件**：用 `-maxrregcount` 强制每线程寄存器数，扫到 kernel 无法启动为止 →
  每 SM 寄存器总量 = max_regs_per_thread × 最大线程数（在 1 CTA 情形下）。

## 4. 证据链规范

每条结论写入 `notes/inference-log.md`，格式固定：

```
### 结论：<一句话>
- 测量：<probe 名> <参数> → <数值>（结果目录 <timestamp>）
- SASS：<关键指令序列>
- 反证：<如果假设成立，应当观察到 X；实测 Y → 排除>
- 置信度：高/中/低
```

**没有 SASS 或没有反证检验的数字，一律标为"待验证"。**

## 5. 已知的坑

- `clock64` 本身有开销（约数十周期），必须靠差值法与足够大的 N 摊薄。
- 内核启动有 ~2-5 µs 开销，绝不用于单条指令测量。
- WDDM 下 `cudaEvent` 精度与调度抖动都差，仅用于粗粒度（>100 µs）测量；
  毫秒级的内核（带宽）反而更适合墙钟。
- `-use_fast_math` 会改变指令选择，**全局禁用**。
- `printf` / 越界访问会触发异常路径，**禁止**出现在测量内核中。
- 编译器会删除"结果未被使用"的计算；所有测量内核必须把结果写回 global memory。
- **重复的相同访存会被合并**：n 条完全相同的 `ld.shared` 会被 ptxas 折成 1 条；
  即使地址不同、但**都写同一个目标寄存器**，前面的结果也会被当成死值删掉。
  对策：每条访存的结果必须被消费（累加进多个累加器），并用 SASS 条数校验。
- **跳数决定实际工作集**：指针追逐里，实际碰到的 cache line 数 ≤ 跳数。
  跳数不足时，大 footprint 会塌缩成小工作集（表现为"DRAM 和 L2 一样快"）。
  对策：跳数 ≥ 4 × (footprint / 128B)。
- **工作集的地址必须是伪随机的**：等步长环会在 cache set 上产生别名冲突，
  让 32 KiB 跑出比 64 KiB 还高的延迟。对策：编号域走整环、地址域走双射混淆函数。
