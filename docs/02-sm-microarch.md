## 1. SM 结构（据实测重建）

```
                        一个 SM（共 24 个）
  ┌──────────────────────────────────────────────────────────────┐
  │  调度器 0          调度器 1          调度器 2          调度器 3   │
  │  (1 条IPC)         (1 条IPC)         (1 条IPC)         (1 条IPC) │
  │     │                 │                 │                 │     │
  │  ┌──▼──────────┐   …  │              …  │              …  │     │
  │  │ FP32   32 宽 │      │                 │                 │     │
  │  │ INT-add 32 宽 │     │                 │                 │     │
  │  │ INT-mul 16 宽 │     │                 │                 │     │
  │  │ SHF/LOP 16 宽 │     │                 │                 │     │
  │  │ SFU     4 宽 │      │                 │                 │     │
  │  └──────────────┘      │                 │                 │     │
  └──────────────────────────────────────────────────────────────┘
     FP64 2 宽（整个 SM 共用，无法定位到分区）
     寄存器 64K × 32bit = 256 KiB   共享内存 100 KiB（驱动上限）
     warp 上限 48   线程上限 1536   CTA 上限 24
```

FP32 = 4×32 = **128 lane/SM**，与 24 SM × 128 = **3072** 个 CUDA core 的规格完全对上，
且与实测峰值 127.5 ops/cyc 一致。

## 2. 怎么证明是 4 个调度器（而不是 2 个或 8 个）

这是整份报告里证据最硬的一条。方法是**只增加 warp 数，看吞吐怎么涨**（单 CTA、单 SM，
每线程 256 条互相独立的 FFMA）：

| warp 数 | 1 | 2 | 4 | 6 | 8 | 12 | 16 | 24 | 32 |
|---|---|---|---|---|---|---|---|---|---|
| FFMA ops/cyc | **32.0** | **63.5** | **127.0** | 96.0 | 126.0 | 125.7 | 127.0 | 125.5 | 127.5 |

读数方式：单条 warp 指令 = 32 个线程各做 1 次 FMA，所以「32 ops/cyc」正好等于
**1 条 warp 指令/周期**。

推理与反证：

1. 1 warp → 32 ops/cyc：**单个 warp 每周期发 1 条指令**。
   （若每条指令有 2 个周期才能发完，这里应是 16。实测 32。）
2. 2 warp → 63.5，4 warp → 127.0：**严格线性**，每加一个 warp 就多 32。
   说明每个新增的 warp 都落在**不同的调度器**上，各自满速 1 IPC。
3. ≥8 warp → 停在 126~128 不再涨：**总发射被卡在 4 条指令/周期**。
4. 假设检验（两个都必须能排除）：
   - 若只有 **2 个**调度器、每个 64 lane：1 warp 就应给出 64 ops/cyc。实测 32 → **排除**。
   - 若有 **8 个**调度器：8 warp 就应给出 256 ops/cyc。实测 126 → **排除**。

⇒ **4 个调度器，每调度器 1 IPC × 32 lane = 32 ops/cyc，SM 峰值 128。**

### 一个没解释掉的异常

`6 warp → 96.0 ops/cyc`（= 3 IPC，而不是 4 IPC）。所有算子都出现同样幅度的 6-warp 低谷
（ffma 96、imad 47、shf 48、mufu 12），8 warp 以上就恢复正常。

- 6 warp 分到 4 个调度器必然是 2/2/1/1，理论上每个调度器仍有 ≥1 个 warp，
  4 个调度器都应能发满 1 IPC，**不该只有 3 IPC**。
- 可能原因：(a) warp→调度器的映射不是 `warpid % 4`，6 个 warp 出现 3/1/1/1 之类的偏斜；
  (b) CTA 启动期 warp 上线不同步；(c) 某些 warp 被绑到同一个调度器且该调度器的
  双 warp 共享了某个队列。
- 状态：**未验证**，留到 Round 4（见 `docs/03-roadmap.md`）。

## 3. 各流水线的宽度

同一套 warp 扫描，饱和值即通道数：

| 算子 | 饱和吞吐（ops/cyc/SM） | 折算每调度器通道 | 判读 |
|---|---:|---:|---|
| `fma.rn.f32` | **127.5** | 32 | FP32：满宽 |
| `add.u32`（IADD3） | **128.0** | 32 | 整数加：满宽（复用 FP32 加法器） |
| `mad.lo.u32`（IMAD） | **67.8** | 16 | 整数乘：半宽 |
| `shl.b32` / `shf.l.wrap` | **64.0** | 16 | 移位：半宽 |
| `xor.b32`（LOP3） | **58.7** | ~16 | 逻辑：半宽（受折叠影响，见下） |
| `fma.rn.f16x2`（HFMA2） | **67.9** | 16 | 每条含 2 个 FP16 → **128 FP16 FLOP/cyc** |
| `ex2.approx.ftz`（MUFU） | **16.0** | 4 | SFU：1/8 宽 |
| `fma.rn.f64`（DFMA） | **2.0** | 0.5 | FP64：全 SM 只有 2 个通道 |

几条值得指出的读数：

- **FP16 不占便宜**。HFMA2 只有 64 条指令/周期，虽然每条算 2 个 FP16，合计 128 FLOP/周期——
  和 FP32 的 128 FLOP/周期**完全一样**。这与「Ada 消费卡 FP16 非张量算力 = FP32 算力」
  的公开说法吻合。换句话说 FP16x2 只是把两个半字塞进一条指令、省一半发射槽，
  并不增加算术吞吐。
- **SFU 是 4 个/调度器**（16/SM），是 FP32 的 1/8。
- **FP64 是 2 个/SM**，正好 127.5/2 ≈ 64，即 **1/64**。这与 4090 那一代消费卡的
  FP64:FP32 = 1:64 的公开比值一致，也解释了为什么 DADD 延迟高达 48 周期。
- **整数乘/移位/逻辑只有 16/调度器**，但**整数加能跑满 32/调度器**。
  合理解释：整数加法器直接复用了 128 个 FP32 加法器，而乘/移位/逻辑走的是
  每分区 16 个的 ALU 通道。这一点与「Volta 以来每分区 16 个 INT32 单元」的公开描述
  部分吻合——但"整数加满宽"这一条是新发现，公开资料通常只说 INT32 = 64/SM。

### LOP3 为什么只有 58.7

逻辑运算的链**在数学上无法保持串行**：任何单比特布尔函数反复迭代，必然在 1~2 步内进入
不动点（`and`/`or` 幂等、`xor`/`not` 自逆、常函数一步到底）。实测时 ptxas 把 8 条 xor 环
中的 4 条消掉（SASS/轮 = 4.0 而非 8.0），剩下的 4 条链 ILP 减半，所以只跑到 58.7。
真实值大概率是 **64**（与 SHF 同为半宽），但严格说这是**推断**。

同理，`rcp.approx` 的延迟无法用重复链测（`rcp∘rcp` 是恒等，必被折叠）——
Round 1 里保留这一行作为对照，值为 0 且已标为无效。

### 3.1 重要限定：128 这个峰值需要「操作数可复用」（Round 7）

上面的 127.5 是用 `a_k = a_k * b + c` 测的——8 条链共用同一对 `b`/`c`，
相邻指令反复读同样的寄存器，操作数收集器可以复用，每条指令实际只需 1 次新的寄存器读取。

Round 7 把三个源改成**全不相同**（`d_k = d_k*b_k + c_k`，SASS: `FFMA R23, R21, R23, R16`，
256 条里只有 1 条带 `.reuse`），吞吐掉到 **78.0**：

| 源寄存器模式 | ops/cycle | `.reuse` 条数 | 溢出 |
|---|---:|---:|---:|
| 3 个全不同 | **78.0** | 1/256 | 0 |
| 2 个不同 | 125.1 | 32/256 | 0 |
| 1 个（全相同） | 125.1 | 0/256 | 0 |

已排除溢出与指令数差异，所以差异只来自**操作数供给**。
代价是 1.60×（约 1.6 周期/条）。

**所以「FP32 峰值 128」的准确说法是**：当操作数可复用时（真实 GEMM 内层循环正是如此：
累加器 + 两个被复用的矩阵元素），FP32 能跑满 128；否则（全不同源）只有 78。
详见 `docs/07-operand-supply-and-scaling.md`。

**Round 8 进一步收窄了机制**：从 SASS 里取出全部 224 条 FFMA 的三源寄存器号，
对候选 bank 数做拟合——2 bank 预测 64（差 18%）、4/8 bank 预测 93（差 19%）、
16/32 bank 预测 128（差 64%），**全都对不上**；
而"寄存器堆每 lane 只能供 2 次读、FFMA 要 3 次"这个**与寄存器分布无关**的模型
预测 `128×2/3 = 85.3`，实测 78，差 9.4%——是唯一接近的。

所以证据倾向**读端口/带宽限制，而不是 bank 冲突**（但仍未定论，残差 9.4% 没解释）。

| 指令 | SASS | 延迟（周期） | 判读 |
|---|---|---:|---|
| `fma.rn.f32` | `FFMA` | **4** | 经典 4 级 |
| `add.rn.f32` | `FADD` | **4** | |
| `mul.rn.f32` | `FMUL` | **4** | |
| `mad.lo.u32` | `IMAD` | **4** | 整数乘加也是 4 |
| `add.u32` | `IADD3` | **4** | 见下，被 ptxas 两两融合成 IADD3 |
| `shl.b32` | `SHF.L.U32` | **4** | |
| `fma.rn.f16x2` | `HFMA2` | **4** | |
| `cvt.rzi.s32.f32` / `cvt.rn.f32.s32` | `F2I` / `I2FP` | **11.5** | 转换走独立较慢通路 |
| `ex2/lg2/rsqrt.approx.ftz` | `MUFU.*` | **17** | SFU |
| `add.rn.f64` | `DADD` | **48** | FP64，2 通道/SM |

## 4. 指令延迟（单 warp 串行依赖链）

### IADD3 那一条：ptxas 帮我们测出了 4

源码里写 320 次 `add.u32 a, a, b`，ptxas 实际只发了 **160 条 `IADD3`**——因为 `IADD3`
是三操作数加法（`R = Ra + Rb + Rc`），一条能顶两次加（`a+b+b`）。

于是：
- 按源码条数算 = 2.004 周期/次加 → 看起来「加法只要 2 周期」
- 按**真实 SASS 条数**归一 = **4.008 周期/条 IADD3**

后者才是微架构的真值。这件事本身也是一个结论：**在依赖链上，整数加的实际成本是 2 周期/次**
（因为相邻两次会被编译器融进一条 IADD3），这在本工程里直接反映了 ptxas 的化简能力。

### MUFU 的 17 周期怎么来的

SFU 只有 4 条通道/调度器，一个 warp 的 MUFU 要 **32/4 = 8 个周期**才能流过 SFU。
依赖链上测得 17 ≈ 8（排空）+ 8（下一条的写入/回读）+ 1，与「窄于 warp 的流水线
其依赖延迟 = 2×占空 + 深度」的模型一致。三个不同 MUFU 算子（EX2/LG2/RSQ）都给出 17，
互相印证。

## 5. FP32 与 INT32 是不是"完全独立的两条管线"？

公开说法常说 Ampere/Ada 的 SM 里 FP32 与 INT32 可以**同时**发射（dual-issue），
理论峰值 128 + 64 = 192 ops/cycle。

实测（4 条 FFMA + 4 条 IMAD 交替的独立流）：

| warp | 1 | 2 | 4 | 6 | 8 | 12 | 16 |
|---|---|---|---|---|---|---|---|
| 混合流 ops/cyc | 18 | 36 | 73 | **110** | 73 | 109 | 148* |

\* 24 warp 的 421 是坏点，已剔除（见方法论）。

结论：最高约 **110 ops/cyc**，**明显低于 192，也低于纯 FFMA 的 128**。
所以在这块 AD107 上，**FP32 与 INT32 并没有表现出完全独立的并发能力**——
更符合「共享同一组 128 个 lane 与 4 条发射槽，IMAD 因为要占 2 个周期而拉低整体」的模型。

这条结论置信度只给"中"：混合流的扫描曲线不平滑（73/110/73/109 来回跳），
说明这套实验设计还不够干净，需要一个更好的探针（见 roadmap）。

## 6. 调度器行为与发射宽度（Round 4）

数据：`results/20261115-213444-final/round4`。

### 6.1 总发射率恰好是 4.00，不存在双发射

混合流：每组 = 8 条 FFMA + 1 条 LDS + 1 条 LOP（LOP 是为了让载入值不被当死值删掉），
4 个 warp，两组（8 组 / 64 组）相减：

| 量 | 值 |
|---|---:|
| dSASS（每线程新增指令数） | 448 |
| dCyc | 448 |
| **总发射率** | **4.00 条 warp 指令/周期/SM** |

`448 / 448 = 1.00 条指令/周期/warp × 4 warp = 4.00`。

判读：若存在双发射（一个调度器每周期发 2 条），FFMA 仍受 128 lane 限制（4 条/周期），
但 LDS 可以额外挤进 1 条/周期，总发射率会到 5 左右。实测**精确地卡在 4.00**，
说明 **每个调度器每周期只发 1 条指令，没有双发射**。

这也解释了为什么 §5 的 FP32+INT32 混合流只有 110 ops/cyc：
两条整数/浮点指令要抢同一个发射槽，不可能叠加到 192。

### 6.2 6-warp 低谷的成因：调度器负载不均

让**每个 warp 自己记录起止周期**（每 warp 跑 256 条独立 FFMA），得到 per-warp 耗时：

| warp 数 | 每 warp 耗时（周期） | 总 IPC | 离散度 |
|---:|---|---:|---:|
| 1 | 262 | 0.98 | 1.00 |
| 2 | 263 262 | 1.95 | 1.00 |
| 3 | 262 263 264 | 2.91 | 1.01 |
| 4 | 265 265 262 262 | 3.86 | 1.01 |
| 5 | **517** 266 263 263 **483** | 2.48 | 1.97 |
| 6 | **517 517** 263 263 **483 483** | 2.97 | 1.97 |
| 8 | 280 280 317 317 522 522 515 515 | 3.92 | 1.86 |
| 12 | 370 533 412 531 749 753 751 751 524 411 526 393 | 4.08 | 2.04 |
| 16 | 534 285 285 397 263 1031 1031 264 753 779 779 751 364 534 534 527 | 3.97 | 3.92 |

三条清楚的事实：

1. **≤4 warp 时每个 warp 都拿到满速 1 IPC**（≈262 周期 = 256 条指令）。
   这再次确认有 4 个调度器，且 warp 数 ≤4 时一调度器一个 warp。
2. **≥5 warp 时 per-warp 耗时出现 2–4 倍分化**（517 ≈ 2×262，1031 ≈ 4×262）。
   这说明 warp 被**不均匀地**放进 4 个调度器：拿到 2 个 warp 的调度器，
   每个 warp 只能 0.5 IPC，于是耗时翻倍。
3. **6 warp 的 3 IPC 就是这么来的**：它被分成 2+2+1+1，
   两个调度器各带 2 个 warp（耗时 517）、两个各带 1 个（耗时 263）。
   内核要等最慢的 warp，所以总 IPC = 6×256/517 ≈ 2.97。
   这不是"6 warp 时硬件变弱了"，而是**负载不均导致快的调度器空转**。

对 Round 2 曲线的解释：FFMA 的 ops/cycle 在 5/6 warp 处下探（Round 2 里 6 warp = 96），
就是因为 warp 数不能被 4 整除。8/12/16 warp 都回到 ~4 IPC（3.92/4.08/3.97）。

### 6.3 Round 6 的补充与修正

Round 6 给每个 warp 记了**绝对起始时刻**，用来排除"错峰启动"这个替代解释：

| warp 数 | 各 warp 起始偏移（周期） | 判读 |
|---:|---|---|
| 6 | 9 2 5 0 1 10 | **同步**（最大 10） |
| 8 | 13 0 2 4 1 8 10 12 | 同步（最大 13） |
| 12 | 10 2 5 0 18 42 45 … | 有错峰（最大 45） |
| 16 | 22 0 2 4 30 28 30 **807** … | 有错峰（最大 807） |

**定性结论保留**：≤8 warp 时所有 warp 在 13 周期内全部启动 ⟹ 双峰不是启动节流，
只能是调度器共享。

**定量结论必须撤回**：把 6 warp 的耗时 `517 522 267 270 363 280` 换算成 IPC
得到 `0.50 0.49 0.96 0.95 0.71 0.91`，**和为 4.51**——超过 §6.1 实测的 4.00 IPC 硬上限。
物理上不可能，说明**单 warp 时间戳在 ≥5 warp 时不具备定量可信度**。
所以「2+2+1+1」只能当作**最合理的定性解释**，不能当作测量结果。

**Round 8 又撤回了另一句**：这里原本写"12/16 warp 的错峰说明 warp 发射有节流"。
Round 8 用极小的 warp 体重测，**32 个 warp 的起始跨度只有 30 个周期**（约 2 周期/warp），
那个 807 周期的偏移没有复现。所以正确说法是「**未观察到明显节流**」。
详见 `docs/08-warp-dispatch-and-bank-fit.md`。

## 7. Tensor Core（Round 5，详见 `docs/05-tensor-core.md`）

| 精度 | SASS | FLOP/cycle/SM | TFLOPS @2.75 GHz | 延迟 |
|---|---|---:|---:|---:|
| FP16 `m16n8k16` | `HMMA.16816.F32` | **513** | 33.6 | 40.5 |
| TF32 `m16n8k8` | `HMMA.1688.F32.TF32` | **257** | 16.8 | 40.8 |
| FP8 `m16n8k32` | `QMMA.16832.F32.E4M3.E4M3` | **1031** | 67.6 | 38.8 |
| INT8 `m16n8k32` | `IMMA.16832.S8.S8.SAT` | **2047** | 135.0 | — |
| INT4 `m16n8k64` | `IMMA.16864.S4.S4.SAT` | **4095** | 270.0 | — |

（INT8/INT4 来自 Round 9，详见 `docs/09-int-tensor-and-tlb.md`。FLOP 按 `2·M·N·K` 计。）

**一个反直觉的点**：INT8 与 FP8 是**同一个形状**（`m16n8k32`）、操作数也都是 8 位，
但 INT8 的发射率是 FP8 的**整两倍**（0.2499 vs 0.1248）——
FP8 路径只跑了半速，原因未查明。INT4 与 INT8 同发射率但 K 翻倍，所以吞吐再翻倍。

- 吞吐严格正比于 K（1 : 0.5 : 2）⟹ 三种精度共用同一条 MMA 流水线。
- 每调度器 128 FLOP/周期 ⟹ 一条 `HMMA.16816` 每 **32 周期**退休一条；
  延迟 40 周期，所以 2 条在飞即可喂饱（4 warp 饱和）。
- `wgmma`（Hopper 的 warpgroup MMA）在 sm_89 上被 ptxas 明确拒绝：
  `Instruction 'wgmma.fence' not supported on .target 'sm_89'`。

### 7.1 稀疏 MMA（Round 6，详见 `docs/06-sparse-and-dispatch.md`）

| | dense f16 | **sparse f16** | dense fp8 |
|---|---|---|---|
| SASS | `HMMA.16816.F32` | `HMMA.SP.16832.F32` | `QMMA.16832.F32` |
| 每条覆盖的 K | 16 | **32** | 32 |
| 发射率（条/周期/SM） | 0.1255 | **0.1257** | 0.1248 |
| 等效 FLOP/cycle/SM | 514 | **1030** | 1022 |
| 有用 FLOP/cycle/SM | 514 | 515 | 1022 |

稀疏指令与 dense **同发射率**，但一次覆盖 K=32（dense 要两条 `m16n8k16`），
所以对 2:4 稀疏矩阵吞吐确实是 2×（等效 1030 vs 514）。
但**有用 FLOP 没有翻倍**：8192 个乘加里一半乘的是零，有效只有 515——与 dense 持平。
换句话说稀疏不是"算得更快"，而是"同样时间吃掉两倍 K、只要一半 A 数据"。

## 9. 存储层次（Round 3，详见 `docs/04-memory-hierarchy.md`）

| 层级 | 容量（实测推断） | 命中延迟 | 折算 ns @2.62 GHz |
|---|---:|---:|---:|
| 共享内存 | 100 KiB/SM（驱动上限） | 24.0 周期 | 9.2 |
| L1（数据） | 32–64 KiB（单 warp 可用） | 37 周期 | 14.1 |
| L2 | 24 MiB（规格）；**可用约 8–12 MiB** | **240–249**（≤8 MiB）→ 458（16 MiB）→ 679（64 MiB） | 91–95（≤8 MiB） |
| DRAM | 8 GiB | 737–849 周期 | 281–324 |

补充实测：显存读 **250.1 GB/s** / 写 **245.1 GB/s**（标称 272 的 92%/90%）；
**DRAM sector = 32 B**（跨步 4→32 B 有用带宽从 217 降到 28 GB/s 后不再下降）；
共享内存 **32 bank × 4 B**，LDS 延迟 23.97 周期。

**TLB（Round 9）**：只访问每条 2 MiB 页的一个 cache line，页数从 4 扫到 256
（512 MiB 地址跨度），延迟**恒为 37.00 周期**——完全没有 TLB 代价。
这排除了 TLB 作为其它实验的干扰项，也说明 L2 段的噪声不是 TLB 造成的。

## 10. 本轮没做到 / 不能声称的

明确列出，避免读者把推断当实测：

1. **L2 的 24 MiB 容量没有被独立确认**：指针追逐在 2–8 MiB 出现未解释的 ~470 周期台阶
   （怀疑是 WDDM 桌面合成占用 L2），容量拐点读不出来，需独占 GPU 重测。
2. **L1 精确容量**只给了 32–64 KiB 的区间，没有更细的网格。
3. **共享内存峰值 32 字/周期是反推的**（由"32 路冲突 = 1 字/周期"），没有直接测到。
4. **TLB**、**LDGSTS/cp.async**：完全没测。
5. **warp→调度器的具体分配规则**：6-warp 低谷已解释为"负载不均"，但为什么是
   槽 0、1 变慢、而不是 `warpid % 4` 预测的槽 0、4，以及 8 warp 为何一半快一半慢，
   都还没有定论。
6. **LOP3 的精确吞吐**：58.7 受折叠污染，真实值推断为 64。
7. **MUFU.RCP 延迟**：原理上不可测（`rcp∘rcp` 恒等），只给了同族 17。
8. **FP32/INT32 并发**：实验不够干净，"未见并发"不等于"证明不能并发"。
9. **IADD3 = 128**：9 个 warp 点里 8 个都是 128，但有 1 个离群点（384），
   且与公开资料冲突，建议换一种探针复核。
10. **寄存器 bank 冲突**、**Tensor Core**：未测。
